# Задание 3. Оценка Data Encryption at Rest and In Transit

| Категория данных | Примеры | Состояние данных | Профиль риска | В чём необходимость защиты | Инструменты и механизмы защиты |
|------------------|---------|------------------|---------------|----------------------------|--------------------------------|
| **1. Прямые идентификаторы (PII)** | ФИО, дата рождения, номер паспорта, СНИЛС, полис ОМС, телефон, email, точный адрес. | **Хранение (At Rest):** В БД EMR.<br>**Передача (In Transit):** Между сервисами, ЛК пациентом.<br>**Использование (In Use):** В интерфейсе сотрудников. | **КРИТИЧЕСКИЙ.** Прямо идентифицируют личность. Утечка ведет к нарушению 152-ФЗ, штрафам, репутационному ущербу, мошенничеству. | Предотвращение несанкционированного доступа и утечки, обеспечение конфиденциальности. | **Шифрование (At Rest):** TDE на уровне СУБД (например, PostgreSQL TDE).<br>**Шифрование (In Transit):** TLS 1.3 для всех соединений (API, веб-интерфейс).<br>**Токенизация:** Замена прямых идентификаторов на случайные токены для использования в тестовых и аналитических средах. Ключи хранятся в Vault.<br>**Маскирование (In Use):** Динамическое маскирование в интерфейсах для сотрудников, которым не нужны полные данные (например, для аналитиков: Иван\*\*\*\* \*\*\*ич). |
| **2. Медицинская тайна (Особо чувствительные данные)** | Диагнозы, история болезни, результаты осмотров и анализов, назначения врачей, медицинские изображения (рентген, УЗИ), генетические данные. | **Хранение (At Rest):** В БД EMR (текст), в защищенном файловом хранилище (изображения).<br>**Передача (In Transit):** Между врачами, лабораториями, системой архивирования.<br>**Использование (In Use):** В рабочем месте врача. | **КРИТИЧЕСКИЙ.** Нарушение врачебной тайны (ФЗ-323). Утечка ведет к дискриминации, психологическому ущербу, шантажу, колоссальным репутационным потерям. | Обеспечение высочайшего уровня конфиденциальности и целостности. Запрет на доступ для немедицинского персонала. | **Шифрование (At Rest):** TDE + дополнительное шифрование на уровне приложения/поля БД для сверхчувствительных полей (например, диагнозы). Файловое хранилище с шифрованием (BitLocker для Windows Server).<br>**Шифрование (In Transit):** Обязательное TLS 1.3. Для интеграции с внешними системами (лаборатории) — VPN или API Gateway.<br>**Строгое управление доступом (RBAC/ABAC):** Только назначенный врач и старший медицинский персонал имеют доступ к данным своего пациента. |
| **3. Финансовые и договорные данные** | Реквизиты договоров, стоимость услуг, история платежей, банковские реквизиты пациента (если есть). | **Хранение (At Rest):** В БД EMR и в "1С:Бухгалтерия".<br>**Передача (In Transit):** Между EMR и 1С, между EMR и платежным шлюзом.<br>**Использование (In Use):** В интерфейсе бухгалтера, кассира. | **ВЫСОКИЙ.** Прямой финансовый ущерб компании и пациенту, нарушение налогового законодательства. | Защита от мошенничества, обеспечение целостности финансовой отчетности. | **Шифрование (At Rest):** TDE в БД EMR и в базе 1С.<br>**Шифрование (In Transit):** Защищенное соединение (TLS) между EMR и 1С (например, через REST API с аутентификацией).<br>**Контроль целостности:** Подписывание финансовых документов электронной подписью (КЭП). |
| **4. Методанные и служебные данные** | Логи доступа, IP-адреса пользователей, технические идентификаторы, данные для аудита (Data Lineage). | **Хранение (At Rest):** В SIEM-системе, лог-файлах серверов.<br>**Передача (In Transit):** Сбор логов с систем в центральное хранилище.<br>**Использование (In Use):** Анализ администратором безопасности. | **ВЫСОКИЙ.** Эти данные являются мишенью для злоумышленников, желающих скрыть свои следы. Их компрометация лишает систему возможности расследования инцидентов. | Обеспечение достоверности и неизменяемости логов для расследования инцидентов. | **Неизменяемое хранилище логов (Immutable Log Storage):** Настройка SIEM-системы или выделенного сервера логов на запись без права удаления/изменения в течение заданного срока.<br>**Централизованный сбор по защищенным каналам:** Использование протоколов Syslog over TLS или агентов с аутентификацией.<br>**Хеширование/ЭЦП логов:** Регулярное подписывание хешей логов для доказательства их неизменности. |
| **5. Обезличенные данные для аналитики** | Агрегированные статистические данные: "количество пациентов 30-40 лет с диагнозом X в филиале Y". | **Хранение (At Rest):** В Аналитическом Хранилище Данных (DWH).<br>**Передача (In Transit):** Из EMR в DWH через ETL/ELT конвейер.<br>**Использование (In Use):** В BI-инструментах аналитиками. | **СРЕДНИЙ.** Риск реидентификации (деанонимизации) при пересечении нескольких агрегированных наборов данных. | Сведение к нулю риска реидентификации личности при сохранении полезности данных для аналитики. | **Дифференциальная приватность (Differential Privacy):** Добавление контролируемого "шума" в результаты агрегирующих запросов. Инструменты: Google Differential Privacy Library, Microsoft SmartNoise.<br>**k-Анонимность:** Обеспечение того, что каждый человек в наборе данных неотличим по определенным атрибутам как минимум от k-1 других людей. Достигается на этапе ETL через обобщение и подавление данных.<br>**Строгий контроль доступа к DWH:** Отдельные учетные записи для аналитиков, запрет на экспорт сырых данных. |
